Zscaler Plugin

Rapid7 InsightConnect · v2.4.2 · Zscaler OneAPI 2024 · OAuth 2.0 Private Key JWT

Description

Zscaler is a SaaS security platform that provides fast, secure connections between client applications, regardless of device, location, or network. This plugin uses the Zscaler OneAPI unified gateway (api.zsapi.net) with OAuth 2.0 Client Credentials authentication to manage security policies across three Zscaler product lines:

  • ZIA (Zscaler Internet Access) — URL categorization, blacklisting, DLP, firewall rules, logs, users, threat feeds
  • ZPA (Zscaler Private Access) — Application segments and server groups
  • ZCC (Zscaler Client Connector) — VPN gateway bypass auditing and management, enrolled device lookup, one-time password (OTP) generation for logout/exit/uninstall

Key Features

  • Lookup categories for a given URL
  • Blacklist or unblacklist URLs
  • Create, delete, and search users
  • Get and update URL categories
  • Manage DLP incidents with time-range filtering
  • List, get, create, and update firewall rules
  • Retrieve web and firewall logs
  • Submit threat feed IoCs (IPs, domains, URLs)
  • Manage ZPA application segments and server groups
  • Audit and manage ZCC VPN gateway bypass entries
  • Send custom API requests for troubleshooting

Requirements

  • A Zscaler OneAPI OAuth 2.0 Client ID from ZIdentity
  • A PEM RSA private key for JWT signing (RS256)
  • The customer vanity domain (e.g., mycompany)
  • The ZIdentity cloud domain, which is the domain of your ZIdentity login URL (commonly zslogin.net or zsapi.net)
  • An API Resource role assigned for each Zscaler service you intend to use (ZIA, ZPA, ZCC)
  • Network connectivity from InsightConnect orchestrator to the ZIdentity domain and to api.zsapi.net on HTTPS (port 443)

Setup & Configuration

Step 1: Create an API Client in ZIdentity

  1. Log in to ZIdentity. Note the domain of your login URL, as it is needed for the Cloud connection field. It is commonly https://{vanity_domain}.zslogin.net but may differ by tenant.
  2. Navigate to Administration > API Clients
  3. Click Add API Client
  4. Configure:
    • Name: Descriptive name (e.g., InsightConnect-SOAR)
    • Description: Purpose of the integration
    • Validation Type: Select Certificates/Public Keys. This plugin authenticates with a private key JWT assertion and does not support the Secret validation type.
    • Resources: On the Resources tab, assign an API Resource role for each service you intend to use (see Permissions section below)
  5. Save and note the Client ID. Copy the full value — it is easy to capture only part of it.
Validation type matters: If the API client is created with the Secret validation type, the token endpoint will reject the plugin's JWT assertion with HTTP 400 invalid_request. The client must be configured with an uploaded public key.

Step 2: Generate and Upload an RSA Key Pair

  1. Generate an RSA private key (2048-bit minimum, 4096-bit recommended): 
    openssl genrsa -out zscaler_private.pem 4096
  2. Extract the public key: 
    openssl rsa -in zscaler_private.pem -pubout -out zscaler_public.pem
  3. In ZIdentity, navigate to the API Client you created
  4. Click Add Public Key and upload zscaler_public.pem
  5. Keep zscaler_private.pem secure — this is what you'll paste into the InsightConnect connection
Security: The private key should never be shared or stored in plaintext outside of InsightConnect's credential vault. Treat it like a password.

Step 3: Configure the InsightConnect Connection

FieldTypeRequiredDescription
Client IDstringRequiredOAuth Client ID from the ZIdentity API Client
Private Keycredential_asymmetric_keyRequiredPEM-encoded RSA private key for JWT signing. Paste the full content of zscaler_private.pem
Vanity DomainstringRequiredYour Zscaler vanity domain (e.g., mycompany). This is the prefix in your ZIdentity login URL.

Set Cloud to match your login URL: The Cloud value is used for the identity endpoint, not the API endpoint. Combined with the vanity domain it forms https://{vanity_domain}.{cloud}/oauth2/v1/token. If it does not match your ZIdentity login domain the connection fails with a DNS resolution error such as Failed to resolve 'mycompany.zsapi.net'. The default of zsapi.net is not correct for every tenant.
How authentication works: The plugin builds a JWT assertion (signed with your private key, RS256), sends it to https://{vanity_domain}.{cloud}/oauth2/v1/token to obtain an access token, then uses that token as a Bearer header for all API requests through api.zsapi.net. A single token is shared across the ZIA, ZPA and ZCC clients, and is cached and auto-refreshed before expiry.

Connection Test Behavior

The connection test validates in two tiers, which lets it distinguish a credential problem from a permissions problem:

  • Authentication is fatal. If an access token cannot be obtained, the test fails. This indicates the client ID, private key, vanity domain or cloud is incorrect.
  • Per-service authorization is informational. Each of ZIA, ZPA and ZCC is probed and the result is written to the job log. The test succeeds as long as at least one service is authorized, so a tenant licensed for only some Zscaler products passes without over-scoping its API client. The test fails only when no service is authorized.

Review the job log after a successful test to confirm which services are available. Actions for an unauthorized service will fail with HTTP 401 until a role is assigned in ZIdentity.

Network Requirements

  • Outbound HTTPS to {vanity_domain}.{cloud} (token endpoint, e.g. mycompany.zslogin.net)
  • Outbound HTTPS to api.zsapi.net (unified API gateway for all ZIA/ZPA/ZCC requests)
  • No inbound connections required
  • If using an HTTP proxy, ensure it allows connections to your ZIdentity domain and to api.zsapi.net

Permissions & OAuth Scopes

Zscaler OneAPI uses OAuth 2.0 scopes to control what the API client can access. Assign the minimum scopes needed for your workflows in the ZIdentity API Client configuration.

Authorization is per service. A token is issued from a single API client but each service enforces its own API Resource role. A client scoped only to ZCC authenticates successfully and still returns HTTP 401 with {"detail": "unauthorized"} for every ZIA and ZPA action. If some actions work and others return 401, open the API client in ZIdentity and check the Resources tab for a role covering each service you use. API Resource roles are derived from the RBAC roles defined within each product, so a role may need to be created in the product admin portal first and then synced in ZIdentity.

Custom API Request

ZIAZPAZCC Send an authenticated request to any OneAPI endpoint and return the raw status code and response body. Unlike other actions this does not raise on a non-2xx response and does not retry on 401, so the exact response is visible. That makes it useful for reproducing a request from Postman or vendor documentation and confirming whether a failure is a plugin issue or a permissions issue.

Input

NameTypeRequiredDescription
ServiceenumRequiredZIA, ZPA or ZCC. Determines the path prefix that is prepended to the path.
MethodenumRequiredGET, POST, PUT, PATCH or DELETE. Default: GET
PathstringRequiredEndpoint path relative to the service prefix, without a leading slash
BodyobjectOptionalJSON body to send. Ignored for GET requests.

Service Prefixes

ServiceResulting URL
ZIAhttps://api.zsapi.net/zia/api/v1/{path}
ZPAhttps://api.zsapi.net/zpa/api/v1/{path}
ZCChttps://api.zsapi.net/zcc/papi/public/v1/{path}

Output

{
  "status_code": 200,
  "url": "https://api.zsapi.net/zcc/papi/public/v1/web/policy/listByCompany",
  "response": "[{\"profileName\": \"Default Profile\"}]"
}
Write methods modify configuration: POST, PUT, PATCH and DELETE will change the target tenant. The action is bounded by the permissions already granted to the connection's API client, so it cannot exceed that scope, but it is a passthrough with no validation of the path or body. Prefer GET when diagnosing.

Troubleshooting

Connection fails with a DNS resolution error

An error such as Failed to resolve 'mycompany.zsapi.net' or Name or service not known means the token endpoint hostname does not exist. The Cloud field must match the domain of your ZIdentity login URL. If you sign in at https://mycompany.zslogin.net then set Cloud to zslogin.net rather than leaving the zsapi.net default.

Token endpoint returns HTTP 400 invalid_request

Authentication reached ZIdentity but the assertion was rejected. Check, in order:

  • The API client's Validation Type is Certificates/Public Keys, not Secret. This plugin only supports private key JWT.
  • The Client ID is the complete value from ZIdentity, not a truncated copy.
  • The private key pasted into the connection is the counterpart of the public key uploaded to the API client. If the key pair was regenerated, both sides must be updated.

Some actions return HTTP 401 while others succeed

A response of {"detail": "unauthorized"} from one service while another service works is an authorization problem, not a credential problem. The token is valid, but the API client has no API Resource role for that service. Open the API client in ZIdentity, go to the Resources tab, and assign a role for each of ZIA, ZPA and ZCC that you intend to use.

To confirm this, run Custom API Request against a service you know works and compare it against the failing one. Differing status codes for the same credentials point to scope.

Confirming which services are authorized

Run the connection test and review the job log. Each service is probed and reported individually, for example:

ZIA: not authorized (OAuth 2.0 bearer token has expired or is invalid.)
ZPA: not authorized (OAuth 2.0 bearer token has expired or is invalid.)
ZCC: authorized
Connection test succeeded. Authorized services: ZCC.
